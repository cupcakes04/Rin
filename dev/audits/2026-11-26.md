## 1. Bugs in current code

### 1.1 Zero-norm vectors in `curate.dedupe` silently drop every remaining frame in the stream (High)
- **Where:** `src/rin/curate/dedupe.py:46-55`, `src/rin/curate/center.py:38-40,50`.
- **What happens:** `dedupe` normalizes `vectors /= np.linalg.norm(vectors, axis=1, keepdims=True)` with no zero-norm guard. When `curate.center` runs on a 1-frame group (an image, a camera with 1 surviving frame, or identical frames), `block - block.mean(axis=0)` is the exact zero vector. Division by `0.0` produces `NaN` (with only a numpy `RuntimeWarning`). In the loop (`float(v @ last) < cosine_max`), `NaN < cosine_max` is `False`. If a zero-norm vector is the first frame in a stream, it is kept as `last = NaN`, and **every subsequent frame in that stream is silently dropped**.
- **Reproduced:** In an isolated temp store with 3 frames in one camera stream whose vectors are `[0, 0]`, `[1, 0]`, `[0, 1]` and `cosine_max=0.99`, `curate.dedupe` returned **1 frame instead of 3**.
- **Related:** `curate.center` casts to `float16` (`center.py:50`) with no `np.isfinite` check (unlike `dinov3.embed`, `src/rin/servants/dinov3/__init__.py:72`) and no guard/warning for 1-frame groups.

### 1.2 `curate.center` and `curate.dedupe` group by `camera` while ignoring `site` and `split` (High)
- **Where:** `src/rin/curate/center.py:28` (`coalesce('camera ' || d.camera, 'media ' || d.media_id)`) and `src/rin/curate/dedupe.py:31-32` (`CASE WHEN d.camera IS NOT NULL AND d.started_at IS NOT NULL THEN 'camera ' || d.camera ELSE 'media ' || d.media_id END`).
- **Why it breaks:**
  1. Two sites with the same camera label (`school/G299` and `hospital/G299`) get averaged together in `center` and interleaved into one stream in `dedupe`.
  2. `center` does not separate by `split` (or day). If an embedding run ever contains `pool` + `val` (or two days with different lighting), `center` mixes their means (leaking split distributions / computing the wrong background mean).
  3. `dedupe` walks clips of the same camera across multi-day gaps as one continuous stream; on a fixed camera where day 1 and day 2 have ~0.95+ similarity, the last frame of day 1 can drop the first frame of day 2.
  4. Inconsistency: `center` groups by `camera` even when `started_at` is null; `dedupe` requires both `camera` and `started_at`.

### 1.3 `motion` score is unnormalized by $\Delta t$, breaking across sampling rates and VFR (Medium)
- **Where:** `src/rin/curate/scores.py:25-27,74-76`.
- **What happens:** `motion` is raw `mean(|frame[k] - frame[k-1]|)` between consecutive rows of the input `frame_set`, regardless of the elapsed time between them.
- **Already visible in `workspace/store/`:**
  - At 2 fps (`20261125-204051-curate.score_frames-72a8`), median motion is `0.0125` and **226 / 14,424** frames fall below `0.002`.
  - At 1 fps (`20261125-205436-curate.score_frames-2666`), median motion is `0.0180` (+44%) and only **4 / 7,224** frames fall below `0.002`.
  - So M2's 1 fps vs 2 fps comparison (`dev/research/m2_filters_dedupe/README.md:11,27-33`) applied a much looser physical motion filter to the 1 fps run than to the 2 fps run.
- **Worse on VFR / non-uniform frame sets:** On VFR video (the exact case D-09 and `test_media.py` care about), a 250 ms gap looks ~7× more active than a 33 ms gap. Frame 0 of each clip also copies `steps[0]` rather than comparing across adjacent clips of the same camera.

### 1.4 `started_at` and run duration lie for CPU steps (Medium)
- **Where:** `src/rin/curate/scores.py:70-87` (and `src/rin/core/sample.py:22-41`, `src/rin/curate/dedupe.py:29-65`, `src/rin/curate/center.py:26-51`, `src/rin/servants/dinov3/__init__.py:57-59`).
- **What happens:** `m.writer(...)` is opened *after* decoding/computation finishes. In `workspace/store/`, `20261125-204051-curate.score_frames-72a8` records `finished_at - started_at = 0.036 s` (and `2666` records `0.016 s`), whereas `dev/research/m2_filters_dedupe/README.md:17` measured 101 s. The `run_id` timestamp is also the end time, not the start time. In `dinov3.embed`, `cached_frames` runs outside `m.writer`, so the 176 s cache build is absent from run duration.

### 1.5 `curate.score_frames(["motion"])` on images-only writes an empty table that crashes `curate.keep` (Medium)
- **Where:** `src/rin/curate/scores.py:74-87,101-113`.
- **Reproduced:** Calling `curate.score_frames(m, fs, ["motion"])` on an image-only frame set succeeds and writes a 0-row `frame_scores.parquet`. Calling `curate.keep(m, sc, where="motion >= 0")` then fails with a raw DuckDB `BinderException: Referenced column "motion" not found in FROM clause!`. Same raw DuckDB error if `where` names any score that wasn't computed in `scores`.

### 1.6 `probe.py` unconditionally sorts timestamps, silently hiding corrupt/non-monotonic MP4/MKV files (Medium)
- **Where:** `src/rin/media/probe.py:77-85`.
- **What happens:** `pts = np.sort(np.asarray(times, dtype=np.float64))` is done for all video containers to work around B-frame AVI files attaching DTS in storage order. On MP4/MKV, this silently masks genuinely corrupt files (e.g. a concatenated CCTV recording whose PTS resets to 0 mid-file) by sorting the timestamps and binding them to the wrong frames, violating `CLAUDE.md:96` ("Fail loudly"). Restricting the sort to `.avi` — or checking that out-of-order jumps never exceed a small B-frame reorder window — keeps MEVA working while catching real PTS resets.

### 1.7 `bool` accepted as numeric argument in `core.sample` and `curate.dedupe` (Low)
- **Where:** `src/rin/core/sample.py:17`, `src/rin/curate/dedupe.py:22`.
- **Reproduced:** `core.sample(m, ing, fps=True)` succeeds with `config={"fps": True}` (1 fps), and `curate.dedupe(m, fs, emb, cosine_max=False)` succeeds with `config={"cosine_max": False}` (0.0). (`dinov3.embed` already guards `isinstance(..., bool)` at `src/rin/servants/dinov3/__init__.py:49,54`.)

### 1.8 `rin/__init__.py` omits `curate`, contradicting `docs/core.md` (Low)
- **Where:** `src/rin/__init__.py:7-11` vs `docs/core.md:42`.
- **Reproduced:** `uv run python -c "import rin; print(hasattr(rin, 'curate'), rin.__all__)"` prints `False ['Master', 'Run', 'core']`. `from rin import Master, core, curate` works only via Python's submodule import fallback, not `rin`'s public exports.

### 1.9 Thread-safety and unpinned/online HF loading in `dinov3/job.py` (Low–Medium)
- **Where:** `src/rin/servants/dinov3/job.py:38-42,50-67,89-97`.
- `ThreadPoolExecutor(max_workers=3)` calls the same `DINOv3ViTImageProcessorFast` instance concurrently from 3 threads (`job.py:55,61-67`); HF processors are not guaranteed thread-safe.
- `from_pretrained(spec["model"])` does not pass `local_files_only=True` or accept a `revision` (unlike `vendors/gemma_emb_engine`, which pins revisions and loads offline by default, `vendors/gemma_emb_engine/README.md:21`). `_revision(model)` (`job.py:94`) reads `refs/main` from cache *after* loading, which isn't guaranteed to match if multiple revisions exist or if upstream updates.
- Minor: `job.py:74` always computes `mean_patch` even when `what == ["cls"]`, and `job.py:71-76` checks `isfinite` in float32 *before* casting to float16 (though `dinov3/__init__.py:72` catches float16 overflow afterwards).

## 2. Biggest trap before M3: `workspace/store/` is about to hold irreplaceable human work

- **Where:** `src/rin/core/ingest.py:108-113`, `src/rin/store/views.py:25-27`, `dev/notes/state.md:41`, `docs/core.md:71`, `dev/notes/decisions.md:80` (D-31), `.gitignore:2`.
- **The collision:**
  1. `state.md:41` and `docs/core.md:71` treat `workspace/store/` as derived data: *"delete it and re-run"*.
  2. `core.ingest` assigns **random** `media_id`s (`"m" + secrets.token_hex(4)`).
  3. `workspace/` is gitignored (`.gitignore:2`).
  4. D-31 (`decisions.md:80`) says M4 will hold out some pool-day clips as `split="val"` — yet all 24 pool clips are *already* ingested as `split="pool"` (`20261124-233555-core.ingest-e1c4`). Because runs are immutable and `ingest` refuses duplicate paths (`ingest.py:42-44`), changing a clip's split currently forces deleting `workspace/store/` and re-ingesting.
  5. `views.py:26` uses `read_parquet(...)` without `union_by_name=true`, so adding a nullable column to any table schema in M3–M6 will break queries on existing Parquet runs unless the store is wiped or migrated.
- **Consequence:** Once M3 writes human judgments, `sam3.click`, and `human.annotate` runs into `workspace/store/`, wiping the store to re-ingest for D-31 or a schema tweak will **destroy or orphan hours of manual checking** (because every re-ingested file gets a new random `media_id`).
- **Fix before M3:**
  1. Make `media_id` deterministic from file content (e.g. sha256 prefix, or file size + head/tail hash) so re-ingesting the same file always produces the same `media_id`.
  2. Add `union_by_name=true` in `views.py:26` so forward-compatible schema additions don't break existing runs.
  3. Separate or back up human-authored ground truth (judgments / clicks / drawn boxes, keyed or exportable by relative media path + `frame_idx`) outside the "safe to delete" mental model — and decide the `val` clips *before* M3 starts.

## 3. Problems with the holy grail experiment

### 3.1 The MEVA slice (2 cameras of one continuously busy indoor gym) is a poor testbed for D-17's "half the labels" bar
- **Where:** `dev/notes/heavy_data.md:21-22`, `dev/notes/decisions.md:36` (D-17), `dev/research/m2_filters_dedupe/README.md:19,23,35`.
- **What the data actually looks like:** Looking at `motion_bands_G299.jpg`, `dropped_at_0.98.jpg`, and `dropped_at_0.99.jpg`, **G299 and G330 film the exact same indoor gym simultaneously from opposite corners** under constant fluorescent lighting during one continuously busy hour. `motion >= 0.002` keeps **98.4%** of frames.
- **Why this risks a false negative:** Curation beats random by ≥2× when raw video has strong redundancy/imbalance (idle stretches, long static regimes, multi-scene or lighting shifts). When almost every frame of the hour already shows 10–30 people in the same room under the same lights, 100–250 random frames already cover the room densely. Failing D-17 on this slice may tell you more about the slice's lack of diversity than about whether curation works.
- **Suggested check:** Either broaden the pool using other cameras/sites/hours already in `mevadata-public-01/drops-123-r13/` (outdoor entrances, parking lots, hallways, idle stretches, lighting changes), or explicitly acknowledge that a single busy indoor gym tests *fine-grained foreground diversity* rather than *raw-stream curation*.

### 3.2 `random` on `cands` is not a raw-video random baseline
- **Where:** `dev/notes/usage.md:232-245`.
- `usage.md:239` runs `random`, `kcenter`, and `kmeans_stratified` on `cands` (4,453 frames) — which has **already been filtered by `motion` AND de-duplicated by DINOv3**!
- `usage.md:245` notes *"Worth adding: random over frames (before filters) as a fourth line"* as an optional extra. That should be the **primary** baseline (otherwise you aren't testing DINOv3 curation vs random, you're only testing stage-2 coreset vs random-after-DINOv3-dedupe).

### 3.3 Missing N = 0 (zero-shot pretrained YOLO) and cheap non-embedding baselines
- **Where:** `dev/notes/usage.md:260-277`, `dev/notes/decisions.md:33-36`.
- Stock `yolo26s` (`usage.md:270`) is COCO-pretrained on `person` (class 0). Without measuring **N = 0 (stock `yolo26s` before any fine-tuning)** on the checked test set, you won't know whether 100 frames is improving the model by +20 mAP or only +2 mAP (within seed noise), or even *hurting* it due to SAM3 pseudo-label misses.
- Also add a cheap CPU baseline: **uniform-in-time stride** and/or **top-N by `motion`**. If uniform-in-time or high-motion matches DINOv3 `kcenter` with zero GPU cost, the experiment should surface that.

### 3.4 Frame-budget vs box-count confound
- **Where:** `dev/notes/usage.md:234,264-271`, `workspace/store/` (`curate.dedupe-818a`).
- Querying `curate.dedupe-818a` (`cosine_max=0.99`) by clip shows survival ranges from **10.1%** (`G299 10:40`) to **65.1%** (`G330 10:00`) — busy clips survive up to 6.4× more often.
- Similarly, centered-vector norms in `20261125-220754-curate.center-eec7` range from `1.98` (sparse/average) to `9.52` (big foreground crowd). If `kcenter` selects frames with ~2× as many people per frame as `random`, then "budget N = 250 frames" gives `kcenter` ~2× the labelled person instances.
- **Fix:** Plot test mAP against **both frame count N and total labelled person boxes** (and log mean people/frame per method).

### 3.5 Distant bleacher crowds & automation bias threaten M3's test set and M5's ceiling
- **Where:** `dev/research/m2_filters_dedupe/motion_bands_G299.jpg`, `dropped_at_0.98.jpg`, `dev/notes/ideas/holy_grail.md:90`, `dev/notes/decisions.md:54,72` (D-13, D-27), `dev/notes/usage.md:191-206`.
- Both G299 and G330 show **20–40 tiny (~15–30 px), heavily occluded dark silhouettes sitting shoulder-to-shoulder on the bleachers** in nearly every frame.
- Three concrete risks:
  1. **M3 annotation cost:** Checking 300 frames × 15–30 people/frame = **4,500–9,000 boxes** to audit, with heavy ambiguity ("is that 15 px blob a seated person or a coat/backpack?"). Because SAM3 internally resizes to `1008×1008` (`dev/rin_v1/docs/notes/services/sam3/usage.md:287`), a 25 px person at 1080p shrinks to ~13 px wide.
  2. **Automation bias in review:** Showing SAM3 overlays first and asking a person to tag frames `complete` / `incomplete` guarantees rubber-stamping under fatigue: reviewers miss the exact tiny/occluded people SAM3 missed, quietly pulling the "human-checked" test set back toward "agreement with SAM3" (the failure D-13 exists to avoid).
  3. **Train/test label mismatch:** If SAM3 systematically misses distant bleacher people on training frames (unchecked, `usage.md:258`), while a person dutifully clicks/draws them on the test set (D-27), *every* student is trained to suppress distant bleacher people as background, creating a low mAP ceiling that can swamp differences between selection methods.
- **Also:** The 300 test frames come from only 15 minutes per camera (1 frame every ~6 s), so the exact same seated bleacher crowd repeats across most of the test set (low effective sample size).
- **Suggested M3 pilot:** Before checking 300 frames, **blind-count/mark 15–20 test frames with SAM3 hidden**, *then* reveal SAM3's predictions and measure its recall/precision by box height (<32 px, 32–64 px, >64 px) and time-per-frame. That calibrates your eyes against automation bias and immediately tells you whether you need tiled SAM3, `iscrowd` / ignore regions, or a wider camera/time sample.

### 3.6 Outlier × pseudo-label noise trap (`kcenter` on unchecked SAM3 labels)
- **Where:** `dev/notes/usage.md:232-258`, `dev/notes/ideas/holy_grail.md:49,89`.
- `kcenter` (farthest-point) actively selects extreme/outlier frames (unusual occlusions, dense foreground crowds, motion edges)—which are often the *exact* frames where SAM3's unchecked pseudo-labels are noisiest.
- If `random` gets cleaner SAM3 pseudo-labels than `kcenter`, `kcenter` can lose in M5 even if its frames were more informative.
- **Check in M4/M5:** Compare SAM3's confidence distribution and spot-check ~20 labelled frames from `kcenter` vs `random` to separate *frame-selection quality* from *teacher-label noise*.

### 3.7 Single scalar `mAP50-95` can hide or distort the M5 verdict
- **Where:** `dev/notes/usage.md:282-290` (`x.name = 'mAP50-95'`), `dev/notes/data_model.md:133`.
- Overall `mAP50-95` mixes large foreground walkers, tiny 15–30 px bleacher silhouettes, and empty-frame false positives into one number. If SAM3's misses cap `mAP_small` near zero for every method, overall mAP compresses and can hide a real 2× win on `mAP_medium` / `mAP_large` (or hide false-positive differences on empty frames).
- **Fix in M5:** Log sliced metrics into `metrics` (`mAP50-95`, `mAP50`, `mAP_small`, `mAP_medium`, `mAP_large`, and false-positives-per-empty-frame) so the M5 verdict sees *where* each method gains or loses.

### 3.8 Geometric trap in `curate.center` for M4 selection
- **Where:** `src/rin/curate/center.py:37-40`, `dev/research/m2_filters_dedupe/README.md:37,44`.
- Measuring `20261125-220754-curate.center-eec7` on `workspace/store/`:
  - Cross-camera `G299` vs `G330` median cosine drops from `0.837` (raw) to `-0.005` (centered), and within-camera median cosine drops to `~0.0`.
  - Centered vector norms vary 5× (`1.98` to `9.52`).
- **Two M4 traps:**
  1. If M4 runs **cosine** farthest-point on centered vectors, L2-normalizing blows up tiny noise residuals near the camera mean (`norm 1.98`) to unit length — two near-average frames with slight noise in opposite directions have cosine similarity **-1.0** (maximum distance!), so cosine `kcenter` can actively select noisy average frames!
  2. Centering each camera independently maps *both* G299 and G330 onto spheres centered at the origin `0`, so joint `kmeans` / `kcenter` mixes the two cameras arbitrarily instead of respecting camera strata. M4 should explicitly decide whether selection runs **per camera** (with proportional or equal camera budgets) vs jointly, and compare **Euclidean** vs **cosine** on centered vectors.

### 3.9 `kmeans_stratified` vs D-28's nested prefix budgets; `kcenter` seed variance
- **Where:** `dev/notes/decisions.md:74` (D-28), `dev/notes/usage.md:232-243`, `dev/notes/ideas/holy_grail.md:49-50`.
- For `kmeans_stratified` to satisfy D-28 (budget N = prefix `rank < N`), $K$ must be fixed at $K \le \min(\text{budgets})$ (e.g. $K \le 100$) with round-robin ranking across clusters — not $K = N$. That design constraint isn't written down yet.
- For `kcenter`, even with a random seed start frame (`holy_grail.md:49`), farthest-point quickly converges to the same extremal outliers after a few steps; expect its seed spread in M5 to reflect mostly YOLO training noise rather than selection variance.

### 3.10 D-31 (`val` split from the pool day) risks temporal leakage and isn't reflected in `usage.md` or `data_model.md`
- **Where:** `dev/notes/decisions.md:80`, `dev/notes/usage.md:263-271`, `dev/notes/data_model.md:74`.
- Holding out 5-minute clips from the same 1-hour gym recording puts `val` 0.5 s away from adjacent `pool` clips (same people, clothes, bleacher positions). Better to pull 2–4 clips from a **different hour** of 2018-03-07 (or a third day) via `pull_meva.sh` for `split="val"`.
- Also `data_model.md:74` still says *"Selection refuses `test` media"* and doesn't list `val` at all; selection should **whitelist** `split == 'pool'` (not blacklist `'test'`), and `core.ingest` should validate or warn on unexpected split names.
- `usage.md` C3 (`usage.md:263-271`) still has no `val` input to `export.yolo` / `yolo.train`.

## 4. Lessons from `rin_v1` (and vendors) that v2 lacks or should note before M3

1. **Durability / `fsync` on atomic writes (v1 CR-4):**
   - v1 learned to `fsync` both file and parent directory before/after `os.replace` (`dev/rin_v1/src/rin/data/core/persistence.py:90-102`).
   - v2's `RunWriter.__exit__` (`src/rin/store/writer.py:132-133`) and `_write_jpeg` (`src/rin/servants/frame_cache.py:53-54`) do not `fsync`. `Master.__init__` (`src/rin/master.py:28`) explicitly cites WSL2 crashes — a hard crash can leave a 0-byte `run.json` in `runs/` (breaking `read_json('runs/*/run.json')` for the entire store) or a 0-byte JPEG in `frames/` (which `f.exists()` at `frame_cache.py:38` treats as valid). Also nothing warns about or cleans leftover `*.partial` files in `store/frames/`.
2. **No `is_crowd` / ignore regions on `instances`:**
   - v1 carried `is_crowd` on every spatial/detection/observation record (`dev/rin_v1/src/rin/data/core/recorder.py`, `S-ADR-22`). v2's `instances` table (`dev/notes/data_model.md:95-108`) dropped it. On crowded CCTV bleachers, an ignore/crowd flag is standard COCO/YOLO evaluation hygiene.
3. **`sam3_engine` batching & `numpy<2` constraints for M3:**
   - `vendors/sam3_engine/docs/api/image-session.md:6`: opening an `ImageSession` runs the vision backbone for **all** images at once. v1 had to chunk into `batch_size = 8` (`dev/rin_v1/src/rin/services/ground/sam3/engine.py:345`) to fit in 16 GB VRAM. M3's `sam3.concept` job must chunk images into small sessions (closing each) while reusing one `Sam3Engine`.
   - `vendors/sam3_engine/pyproject.toml:18` pins `numpy>=1.26,<2` (core Rin and DINOv3 use `numpy>=2`). Servant venv isolation (D-07/D-20) handles this cleanly, as long as exchange files use plain JSON / `.npy` / RLE strings (no pickled numpy objects).
4. **v1 stored clip duration / frame spans; v2 stores only frame start `pts`:**
   - v1's `TimeCoder.read_frame_spans` (`dev/rin_v1/src/rin/codecs/timecoder.py:79-89`) and `test_vfr_timing.py:38-43` preserved the end time of the last frame. In v2, `max(pts)` understates duration by one frame (which matters for VFR clips and later action windows).
   - Also check `usage.md:104`: `# 14,424 (2 cameras × 3600 s × 2)` — `2 × 3600 × 2 = 14,400`. The extra 24 frames are because each 5-min MEVA clip has 9,006–9,010 frames (`max_pts ≈ 300.23 s`), so `sample(fps=2)` picks `t = 0.0 … 300.0` = 601 frames per clip (`24 × 601 = 14,424`).
5. **v1 CR-28 / `data_model.md` geometry & mask validation:**
   - Already noted in `lessons/rin_v1.md:56` for M3 (`enforce_unit_geometry`), plus check `x0 < x1` and `y0 < y1` (degenerate zero-area boxes from rounding). Note also `data_model.md:104`: `mask_rle` is typed as `str or null` (counts string only, since media `width`/`height` are in `media` — make sure RLE encoding/decoding explicitly agrees on `(height, width)` order and UTF-8 string counts, as in `dev/rin_v1/src/rin/codecs/spatial_ops/convert.py:135-155`).

## 5. Data model, API, and provenance gaps

### 5.1 `judgments` is missing `class` (in addition to the open multi-run question in `decisions.md:90`)
- **Where:** `dev/notes/data_model.md:136-156`, `dev/notes/decisions.md:90`.
- `data_model.md:151` defines `frame, accept` as: *"every object of the class on this frame is labelled"*, yet the `judgments` table has **no `class` column**. As soon as a second class (e.g. `vehicle`, `backpack`) is labelled on the same footage, a frame `accept` cannot say which class was checked.
- For the open multi-run completeness question (`decisions.md:90`), storing frame completeness with `(class, covering_run_ids)` (or judging a frozen label-set/snapshot) cleanly records *which* runs and *which* class were verified complete without falsely claiming SAM3's run alone was complete.

### 5.2 Provenance (`code_version`) is currently always `src_dirty: true` and doesn't track vendor commits
- **Where:** `src/rin/store/writer.py:31-45`, `dev/notes/data_model.md:59`, `workspace/store/runs/*/run.json`.
- **Observed in `workspace/store/`:** All 24 runs (every M1 and M2 run cited in `dev/research/m2_filters_dedupe/README.md`) have `"src_dirty": true` and record the *previous* commit (`3a3d7fe` or `379f1cc`) rather than `9c924a6`. Because experiments run before the user commits (`CLAUDE.md:101`), `code.rin` never points to the code that actually produced the results. Consider either committing code before final research runs or recording a diff hash/note when dirty.
- `code_version()` also doesn't record vendor submodule commits (`vendors/sam3_engine`, etc.), even though `data_model.md:59` requires *"Git commit of Rin and of the vendor engine used"*.

### 5.3 `usage.md` `gate` references `area`, which is not a column of `instances`
- **Where:** `dev/notes/usage.md:267` (`gate="score >= 0.4 AND area BETWEEN 0.0001 AND 0.5"`) vs `dev/notes/data_model.md:108` (*"The area of a box is a query (`(x1-x0)*(y1-y0)`), not a column."*).
- M3/M4's `m.dataset` will either need a CTE exposing derived columns (`area`, `w`, `h`, `aspect`) before applying `gate`, or `usage.md` should use the real expression.

### 5.4 `curate.center` provenance inconsistency & `Run` properties

## 6. Doubts about the direction and decisions

### 6.1 FiftyOne + offline batch clicking (D-16 + D-07) will hurt in M3
- **Where:** `dev/notes/decisions.md:30,42,88`, `dev/notes/usage.md:191-211`.
- Open-source FiftyOne is great for viewing and tagging (`complete` / `incomplete` frames, `wrong` boxes), **not** for clicking points or drawing boxes natively (it delegates annotation to CVAT / Label Studio).
- Collecting clicks blindly into a JSON file and running `sam3.click` offline as a batch job (`usage.md:211`) is a bad UX loop: single-click SAM3 prompts are inherently ambiguous (part vs whole, `vendors/sam3_engine/docs/api/image-session.md:35`), so you won't know if a click grabbed a jacket instead of the whole person until you re-export and re-open FiftyOne.
- **Recommendation:** Use D-07's explicit interactive exception (*"A long-lived process only for an interactive need (e.g. SAM3 clicks)"*)! Do fast pass/fail triage of all 300 frames in FiftyOne first, then fix *only* the incomplete frames in a tiny local click/draw tool talking to `sam3_engine` live (or CVAT/Label Studio if preferred), which still writes immutable `sam3.click` and `human.annotate` runs into the store at the end.

### 6.2 `D-08` / `D-23` ("every step writes a folder of Parquet") is clean, but watch run clutter
- `workspace/store/runs/` already has 24 run folders after just M1–M2 (13 of them exploratory `curate.dedupe` threshold sweeps). After M5 (36 exports + 36 trains + 36 evals + selections + sweeps), `runs/` will hold 150–200+ folders with no way to mark or archive exploratory/superseded runs (except tags). Adding a simple convention (e.g. `tags={"experiment": "m5_v1"}` and a helper or SQL pattern to filter by tags) will keep `m.runs()` readable without breaking immutability.
